# V0.4-S7 — Operação local no Windows

## Escolha operacional e auditoria

O caminho recomendado no Windows 11 é `.venv` sincronizado pelo `uv` e o entry
point `scripts\start-local.ps1`. O fallback técnico é executar o mesmo script
explicitamente pelo PowerShell. Não há instalador, serviço, daemon, launcher
gráfico, auto-update nem restauração destrutiva.

| Item auditado | Estado | Decisão |
| --- | --- | --- |
| Django/host/porta | Parcial | `runserver` já era local; o entry point fixa `127.0.0.1:8000`. |
| Ambiente e Python | Adequado | `uv.lock`, `.python-version` e `pyproject.toml` fixam Python 3.13.15. |
| Dependências | Adequado | `uv sync --locked` é a única sincronização suportada. |
| Perfis/configuração SQLite | Adequado | Os perfis existentes resolvem bancos por variáveis `CEI_*`; nada é hardcoded. |
| Scripts de operação | Parcial | Havia somente o gate; S7 adiciona um entry point e wrapper de Explorer. |
| Logs | Adequado | Logs JSON sanitizados existentes permanecem autoritativos. |
| S5 e S6 | Adequado | Comandos oficiais existentes são compostos, sem cópia de lógica. |
| Guia de uso/atualização | Parcial | Este guia consolida o procedimento operacional. |
| Atalho/Explorer | Ausente | `start-local.cmd` é o mecanismo equivalente simples. |

## Primeira preparação e início

Na raiz que contém `pyproject.toml`, sincronize exatamente o lock:

```powershell
uv sync --locked
```

Prepare o banco de desenvolvimento somente na primeira vez ou quando a política
de atualização abaixo explicitamente o exigir; o startup nunca executa migration
nem bootstrap:

```powershell
New-Item -ItemType Directory -Force var
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py bootstrap_local --timezone America/Sao_Paulo
```

O caminho recomendado, de qualquer diretório corrente, é:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "C:\caminho\para\o\projeto\scripts\start-local.ps1"
```

Abra `http://127.0.0.1:8000/`. O script não abre navegador: a URL é exibida e
falha de navegador nunca afeta o servidor. Para clique no Explorer, use
`scripts\start-local.cmd` (ou crie um atalho Windows para ele); ambos derivam a
raiz da localização do script e não do diretório corrente. O wrapper usa
`-ExecutionPolicy Bypass` apenas naquele processo, sem enfraquecer a política
global do sistema.

O perfil opcional local com `DEBUG=False` exige uma chave apenas no processo:

```powershell
$env:CEI_SECRET_KEY = .\.venv\Scripts\python.exe -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start-local.ps1 -Profile production_local
Remove-Item Env:CEI_SECRET_KEY
```

O entry point exige `.venv\Scripts\python.exe` com Python 3.13.15, `manage.py`
e, para produção local, `CEI_SECRET_KEY`. Ausências informam o próximo passo;
ele não recorre silenciosamente ao Python global, não baixa dependências e não
altera banco. A porta ocupada é informada sem matar processo e sem trocar para
uma porta aleatória. Para usar outra porta local de modo consciente, passe
`-Port 8001`. Encerre com `Ctrl+C` no mesmo terminal; o script não cria processo
separado ou órfão (o autoreloader Django é desabilitado para manter esse ciclo
de vida único).

## Diagnóstico, backup e recuperação

Execute sempre com o Python da `.venv` e confirme o perfil/banco antes:

```powershell
.\.venv\Scripts\python.exe manage.py check_integrity
.\.venv\Scripts\python.exe manage.py backup_sqlite --output .\backups\cei-AAAAMMDDTHHMMSSZ.sqlite3
.\.venv\Scripts\python.exe manage.py validate_backup --backup .\backups\cei-AAAAMMDDTHHMMSSZ.sqlite3
```

O checker S5 preserva: exit `0` saudável, `2` findings impeditivos e `3` falha
operacional inconclusiva. `2` e `3` não são sucesso: pare uma operação relevante,
preserve evidência e investigue pelos logs sanitizados.

O backup é um par arquivo + manifesto sidecar; preserve ambos em diretório sob
controle do operador. A validação é física, não prova recuperação. Para o fluxo
S6 completo, restaure **somente** em destino novo e isolado:

```powershell
.\.venv\Scripts\python.exe manage.py restore_backup --backup .\backups\cei-AAAAMMDDTHHMMSSZ.sqlite3 --destination .\recovery\cei-AAAAMMDDTHHMMSSZ-verified.sqlite3
```

Exit `0` confirma SQLite, reconciliação e S5 na cópia; `2`/`3` preservam os
significados do checker. Isso nunca substitui o banco principal nem implementa
um restore sobre ele. Consulte `V0.4_S6_Backup_e_Recuperacao.md` para retenção,
RPO/RTO e falhas detalhadas.

## Atualização local segura e troubleshooting

1. Pare a aplicação com `Ctrl+C`.
2. Confira `git status`; não use `git reset --hard` e não faça `git pull` sobre
   mudanças locais não resolvidas.
3. Crie e valide um backup S6 antes de passos que possam afetar os dados.
4. Atualize o código pelo fluxo Git explicitamente escolhido pelo operador.
5. Execute `uv sync --locked`; não use `pip install --upgrade`.
6. Leia as notas da revisão recebida e aplique migrations manualmente apenas se
   essa revisão as declarar. Startup normal não as aplica.
7. Execute a verificação apropriada e inicie novamente pelo entry point.

Problemas comuns: venv ausente → `uv sync --locked`; porta ocupada → identifique
e encerre conscientemente o processo anterior ou escolha `-Port`; banco ausente
ou inválido → confirme a variável `CEI_DEVELOPMENT_DB`/`CEI_PRODUCTION_LOCAL_DB`
e recupere apenas pelo fluxo isolado S6; backup recusado → use nome/destino novo
e preserve manifesto; checker exit 2 → findings impedem continuidade; checker
exit 3 → resultado inconclusivo, confira configuração e logs. Logs são emitidos
no destino configurado pelo perfil e são JSON sanitizado; não registre segredos
em comandos, atalhos ou arquivos versionados.

## Limites

Esta é uma operação local loopback. Não é distribuição pública, hospedagem,
instalador, atualizador automático, serviço residente ou mecanismo de restore
destrutivo. Hardening transversal e piloto continuam em S8 e S9, sem autorização
por este guia.
